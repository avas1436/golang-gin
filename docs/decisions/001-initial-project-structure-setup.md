# ۰۰۰۱: راه‌اندازی اولیه ساختار پروژه

## وضعیت

پذیرفته‌شده

## زمینه

پیش از نوشتن اولین خط کد سرویس‌ها، باید دو تصمیم بنیادی گرفته می‌شد:

۱. آیا کد تمام سرویس‌ها در یک ریپوی واحد (Monorepo) قرار بگیرد یا هر سرویس ریپوی جداگانه خودش را داشته باشد؟  
۲. ماژول‌بندی Go چگونه انجام شود تا هم هر سرویس مستقل بماند و هم کد مشترک (مثل logger، error handling، middleware احراز هویت) بدون کپی کردن، بین سرویس‌ها به اشتراک گذاشته شود؟

پاسخ به این دو سوال، شکل نهایی ساختار پوشه‌های پروژه را تعیین می‌کند.

## گزینه‌های بررسی‌شده

**Multi-repo (هر سرویس، یک ریپو مجزا)**  
نزدیک‌ترین حالت به دنیای production واقعی و استقلال کامل هر تیم/سرویس را فراهم می‌کند. اما برای یک پروژه تک‌نفره و تمرینی، مدیریت چند ریپو و به‌خصوص اشتراک‌گذاری پکیج مشترک (`pkg`) بین آن‌ها نیازمند publish کردن یک ماژول Go جداگانه یا استفاده از `replace` دستی در هر ریپو است؛ این پیچیدگی برای هدف یادگیری معماری، سربار غیرضروری ایجاد می‌کند.

**Monorepo با یک go.mod واحد برای کل پروژه**  
ساده‌ترین حالت از نظر تنظیمات، اما تمام سرویس‌ها را در یک فضای نسخه‌بندی dependency مشترک قرار می‌دهد. یعنی اگر یک سرویس نیاز به ارتقای نسخه‌ی یک کتابخانه داشته باشد، این تغییر روی همه سرویس‌ها اثر می‌گذارد. این دقیقاً تضاد با فلسفه استقلال سرویس‌ها در معماری میکروسرویس است.

**Monorepo با go.work و go.mod مستقل برای هر سرویس (انتخاب نهایی)**  
هر سرویس ماژول Go کاملاً مستقل خودش را دارد (دقیقاً مثل این‌که در ریپوی جدا بود) اما `go.work` به Go می‌گوید در محیط توسعه محلی، این ماژول‌ها را به‌صورت یکپارچه ببیند. به این ترتیب:

- کد داخل `pkg` بدون نیاز به publish یا `replace` دستی، مستقیماً در هر سرویس قابل import است
- IDE و ابزارهایی مثل `go build`, `go test`, `gopls` تمام ماژول‌ها را همزمان می‌شناسند
- در build نهایی (Dockerfile هر سرویس)، `go.work` نادیده گرفته می‌شود و فقط `go.mod` همان سرویس مبنای build قرار می‌گیرد؛ در نتیجه استقلال واقعی هر سرویس در production حفظ می‌شود

## تصمیم

از ساختار Monorepo با `go.work` استفاده شد. مراحل راه‌اندازی به شرح زیر است:

### ۱. ساخت فایل go.work در ریشه پروژه

<div dir="ltr">

```bash
go work init
```

</div>

### ۲. اضافه کردن هر سرویس و پکیج مشترک به go.work

<div dir="ltr">

```bash
go work use ./services/user-service
go work use ./services/product-service
go work use ./services/order-service
go work use ./services/payment-service
go work use ./services/notification-service
go work use ./api
go work use ./pkg
```

</div>

### ۳. ساخت go.mod مستقل برای هر سرویس

داخل هر پوشه سرویس، به‌صورت جداگانه:

<div dir="ltr">

```bash
cd services/user-service
go mod init user-service
```

</div>

این کار برای `product-service`, `order-service`, `payment-service`, `notification-service`, `api` (Gateway) و `pkg` نیز تکرار می‌شود. نتیجه این‌که هر سرویس مستقل از بقیه، `go.mod` و در نتیجه dependency graph خودش را دارد.

> **نکته درباره نام‌گذاری ماژول‌ها:** برای مسیر ماژول‌ها به‌جای فرمت معمول دامنه‌محور (مثل `github.com/username/repo/services/user-service`) از نام‌های کوتاه و ساده (`user-service`, `pkg` و ...) استفاده شد. این انتخاب مخصوص محدوده فعلی پروژه است: چون این ماژول‌ها هرگز به‌صورت مستقل publish یا از بیرون این ریپو import نمی‌شوند، نیازی به namespace دامنه‌محور نیست و نگهداری مسیرهای کوتاه‌تر در import ها را ساده‌تر می‌کند. اگر در آینده یکی از سرویس‌ها به ریپوی جداگانه منتقل شد یا `pkg` به‌صورت عمومی publish شد، این نام‌گذاری باید به فرمت دامنه‌محور استاندارد تغییر کند.

## ساختار نهایی پوشه‌ها و دلیل هر بخش

<div dir="ltr">

```text
ecommerce-microservices/
├── api/
├── docker/
├── docs/
├── pkg/
├── scripts/
└── services/
    └── {service-name}/
        ├── cmd/
        ├── config/
        ├── internal/
        │   ├── handler/
        │   ├── middleware/
        │   ├── model/
        │   ├── repository/
        │   └── service/
        ├── migrations/
        ├── Dockerfile
        └── go.mod
```

</div>

### توضیحات

- **api/**: جدا از `services` نگه داشته شده چون مسئول مسیریابی و احراز هویت است، نه منطق کسب‌وکار.
- **docker/**: فایل‌های Docker Compose برای اجرای کل سیستم.
- **docs/**: مستندات معماری و ADR.
- **pkg/**: کدهای مشترک بین سرویس‌ها (logger، auth، RabbitMQ و ...) که هیچ منطق کسب‌وکار اختصاصی یک سرویس در آن قرار ندارد.
- **scripts/**: اسکریپت‌های کمکی برای خودکارسازی کارهای تکراری توسعه (migration، تولید کد proto و ...).
- **cmd/**: نقطه ورود (`main.go`) هر سرویس؛ جدا از `internal` تا مشخص باشد چه چیزی executable است.
- **config/**: بارگذاری تنظیمات از متغیرهای محیطی، مخصوص همان سرویس.
- **internal/**: کد اختصاصی همان سرویس که به‌لطف مکانیزم `internal` در Go، توسط ماژول‌های دیگر (از جمله سایر سرویس‌ها) قابل import نیست.
- **migrations/**: فایل‌های Migration مخصوص دیتابیس همان سرویس؛ هر سرویس migration های خودش را مستقل مدیریت می‌کند.

منطق لایه‌بندی داخل `internal`:

- **handler**: لایه HTTP؛ فقط دریافت request، اعتبارسنجی ورودی و فراخوانی لایه service
- **service**: منطق کسب‌وکار؛ هیچ وابستگی مستقیم به Gin یا جزئیات HTTP ندارد
- **repository**: تنها لایه‌ای که مستقیماً با دیتابیس صحبت می‌کند
- **model**: تعریف struct ها و entity های دامنه

این جداسازی باعث می‌شود منطق کسب‌وکار (`service`) کاملاً مستقل از فریم‌ورک وب یا نوع دیتابیس قابل تست باشد؛ برای مثال می‌توان لایه `service` را با یک repository ساختگی (mock) تست کرد بدون نیاز به دیتابیس واقعی یا حتی راه‌اندازی Gin.

## پیامدها

### مزایا

- هر سرویس به‌طور کامل مستقل build و deploy می‌شود؛ تغییر در یک سرویس هیچ اثری روی بقیه ندارد
- کد مشترک در `pkg` بدون نیاز به publish یا نسخه‌بندی جداگانه، در تمام سرویس‌ها قابل استفاده است
- توسعه، تست و دیباگ در محیط محلی به لطف `go.work` بسیار ساده‌تر از حالت multi-repo است
- اگر در آینده نیاز شد یک سرویس به ریپوی جداگانه منتقل شود، چون `go.mod` مستقل دارد، این کار بدون تغییر ساختاری بزرگ ممکن است

### معایب

- باید در Dockerfile هر سرویس دقت شود که build صرفاً بر اساس `go.mod` همان سرویس انجام شود، نه با وابستگی به `go.work` (که فایلی مخصوص محیط توسعه محلی است و نباید وارد ایمیج نهایی شود)
- مفهوم `go.work` نسبت به `go.mod` معمولی کمتر شناخته‌شده است و نیاز به توضیح دارد
- در Monorepo، دسترسی به کد همه سرویس‌ها در یک ریپو وجود دارد؛ این یعنی مرز استقلال سرویس‌ها صرفاً با نظم تیم حفظ می‌شود، نه با محدودیت فیزیکی ریپوی جدا (بر خلاف حالت multi-repo)
- نام‌گذاری ساده ماژول‌ها (بدون namespace دامنه‌محور) تنها برای محدوده فعلی پروژه مناسب است و در صورت انتشار عمومی یا تفکیک به چند ریپو، نیاز به بازنویسی مسیر import ها دارد
