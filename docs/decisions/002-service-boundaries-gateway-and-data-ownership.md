# ۰۰۰۲: تفکیک سرویس‌ها و مالکیت داده

## وضعیت

پذیرفته‌شده

## زمینه

پیش از نوشتن اولین سرویس، سه سوال بنیادی و به‌هم‌مرتبط باید پاسخ داده می‌شد:

۱. سیستم به چه سرویس‌های مستقلی تقسیم شود و مرز مسئولیت هرکدام کجاست؟  
۲. کلاینت‌های خارجی چگونه به این سرویس‌ها دسترسی پیدا کنند؛ از طریق یک Reverse Proxy ساده یا یک API Gateway یا هر دو ؟  
۳. هر سرویس به دیتابیس مستقل خودش دسترسی داشته باشد یا همه از یک دیتابیس مشترک استفاده کنند؟

این سه سوال از هم جدا نیستند: نحوه تفکیک سرویس‌ها مستقیماً روی مرز مالکیت داده اثر می‌گذارد، و نوع نقطه ورود انتخاب‌شده (Gateway/Proxy) تعیین می‌کند چه مسئولیت‌هایی (احراز هویت، Rate Limiting) از دوش خود سرویس‌ها برداشته می‌شود.

## بخش اول: مرز سرویس‌ها (Service Boundaries)

### گزینه‌های بررسی‌شده

**تفکیک بر اساس لایه فنی** (مثلاً یک سرویس برای همه APIها، یک سرویس برای همه پردازش‌های Background)  
این روش رایج ولی اشتباه است چون باعث می‌شود یک تغییر ساده در منطق کسب‌وکار (مثلاً تغییر قوانین ثبت سفارش) به چند سرویس فنی مختلف سرایت کند.

**تفکیک بر اساس قابلیت کسب‌وکار (Business Capability / Bounded Context)** — انتخاب نهایی  
هر سرویس حول یک قابلیت مستقل کسب‌وکار شکل می‌گیرد که تغییرات آن معمولاً به همان سرویس محدود می‌ماند.

### تصمیم

سرویس‌ها بر اساس قابلیت کسب‌وکار تفکیک شدند:

| سرویس                | مرز مسئولیت                    |
| -------------------- | ------------------------------ |
| User Service         | هویت کاربر، احراز هویت، نقش‌ها |
| Product Service      | کاتالوگ محصولات و جست‌وجو      |
| Order Service        | چرخه حیات سفارش و هماهنگی Saga |
| Payment Service      | پردازش پرداخت                  |
| Notification Service | اطلاع‌رسانی بر اساس رویداد     |

قاعده تشخیص مرز: هر سرویس باید بتواند به یک سوال ساده پاسخ دهد — «اگر این قابلیت کسب‌وکار به‌طور کامل تغییر کند (مثلاً قوانین پرداخت عوض شود)، آیا فقط همین سرویس نیاز به تغییر دارد؟» اگر پاسخ نه باشد، مرز اشتباه انتخاب شده است.

## بخش دوم: دیتابیس مشترک یا مجزا؟

### گزینه‌های بررسی‌شده

**دیتابیس مشترک برای همه سرویس‌ها**  
ساده‌ترین حالت پیاده‌سازی، اما اگر چند سرویس مستقیماً به جداول یکدیگر دسترسی داشته باشند، در عمل دیگر یک سیستم میکروسرویس نیست؛ فقط یک مونولیت با پوشه‌بندی کد جداست. تغییر schema توسط یک سرویس می‌تواند بدون هماهنگی، سرویس‌های دیگر را از کار بیندازد.

**یک instance مشترک PostgreSQL با schema جدا برای هر سرویس**  
حالت میانی؛ جداسازی منطقی داده وجود دارد اما همچنان یک نقطه شکست مشترک (instance واحد دیتابیس) باقی می‌ماند و امکان انتخاب نوع دیتابیس متفاوت برای سرویس‌های آینده (مثلاً استفاده از یک موتور جست‌وجوی متفاوت برای Product Service) وجود ندارد.

**دیتابیس کاملاً مستقل برای هر سرویس (Database-per-Service)** — انتخاب نهایی  
هر سرویس PostgreSQL اختصاصی خودش را دارد و هیچ سرویس دیگری مجاز به اتصال مستقیم به آن نیست؛ تنها راه دسترسی به داده یک سرویس، از طریق API یا رویدادهای آن است.

### تصمیم

هر سرویس (User، Product، Order، Payment) دیتابیس PostgreSQL مستقل خود را دارد. Notification Service به دلیل بدون‌حالت (stateless) بودن، نیازی به دیتابیس اختصاصی ندارد.

## پیامدها

### مزایا

- هر سرویس می‌تواند مستقل از بقیه توسعه، تست، deploy و مقیاس‌دهی شود؛ چه از نظر کد (به لطف مرزبندی بر اساس قابلیت کسب‌وکار)، چه از نظر داده (به لطف دیتابیس مستقل)
- منطق‌های امنیتی و Cross-Cutting (احراز هویت، Rate Limiting) در یک نقطه واحد (Gateway) پیاده‌سازی می‌شود، نه در هر سرویس به‌طور جداگانه
- امکان انتخاب فناوری متفاوت برای هر سرویس در آینده وجود دارد (مثلاً موتور دیتابیس متفاوت برای جست‌وجوی محصولات)
- شکست یا کندی یک سرویس (مثلاً Payment) به‌طور مستقیم دیتابیس یا کارایی سرویس‌های دیگر را تحت تاثیر قرار نمی‌دهد

### معایب

- بدون امکان JOIN مستقیم بین جداول سرویس‌های مختلف؛ ترکیب داده از چند سرویس باید از طریق فراخوانی API یا رویداد انجام شود، نه Query مستقیم دیتابیس
- پذیرفتن **Eventual Consistency** به‌جای Strong Consistency بین سرویس‌ها؛ این دقیقاً دلیلی است که به الگوی Saga برای فرآیند سفارش نیاز پیدا کردیم (شرح در `docs/architecture.md`, بخش ۴)
- افزایش پیچیدگی عملیاتی: مدیریت چند migration، چند connection pool و چند backup مجزا به‌جای یک دیتابیس واحد
- احتمال تکرار محدود داده (Data Duplication) بین سرویس‌ها؛ برای مثال Order Service ممکن است یک نسخه ساده از نام و قیمت محصول را در لحظه ثبت سفارش در جدول خودش نگه دارد تا وابسته به فراخوانی زنده و مداوم به Product Service نباشد
- API Gateway به یک نقطه حیاتی سیستم (Single Point of Failure در مسیر ورودی) تبدیل می‌شود؛ باید در طراحی آن به پایداری و Timeout مناسب توجه شود
