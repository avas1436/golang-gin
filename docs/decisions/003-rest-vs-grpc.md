# ۰۰۰۳: انتخاب پروتکل ارتباطی (REST در مقابل gRPC)

## وضعیت

پذیرفته‌شده

## زمینه

سیستم دو نوع مسیر ارتباطی متفاوت دارد که هرکدام محدودیت‌ها و نیازهای خاص خود را دارند:

۱. ارتباط **کلاینت خارجی (وب/موبایل) با API Gateway**  
۲. ارتباط **داخلی بین خود سرویس‌ها** (Gateway به سرویس‌ها، و Order به Product برای رزرو موجودی)

باید تصمیم گرفته می‌شد که در هرکدام از این دو مسیر، از چه پروتکلی استفاده شود؛ آیا یک پروتکل واحد (فقط REST یا فقط gRPC) در کل سیستم به کار رود، یا هر مسیر پروتکل متفاوتی داشته باشد؟

## گزینه‌های بررسی‌شده

**فقط REST در همه‌جا**  
ساده‌ترین حالت از نظر پیاده‌سازی و دیباگ (قابل تست با ابزارهایی مثل curl و Postman بدون نیاز به ابزار خاص) و برای کلاینت‌های خارجی (مرورگر، موبایل) گزینه‌ی طبیعی است. اما برای ارتباط داخلی پرتکرار بین سرویس‌ها، سربار serialize/deserialize کردن JSON و نبود قرارداد نوع‌دار (type-safe contract) بین سرویس‌ها یک ضعف محسوب می‌شود؛ تغییر ساختار یک response در یک سرویس، بدون کامپایل‌تایم‌چک، می‌تواند در زمان اجرا در سرویس مصرف‌کننده باعث خطا شود.

**فقط gRPC در همه‌جا**  
عملکرد بهتر و قرارداد نوع‌دار در سراسر سیستم، اما gRPC به‌طور پیش‌فرض برای فراخوانی مستقیم از مرورگر مناسب نیست (به gRPC-Web و یک Proxy میانی مثل Envoy نیاز دارد) و برای یک پروژه یادگیری، این پیچیدگی اضافه در لایه‌ی کلاینت توجیه ندارد.

**GraphQL به‌عنوان لایه یکپارچه**  
انعطاف بالا برای کلاینت در انتخاب داده موردنیاز، اما یادگیری و پیاده‌سازی صحیح آن (resolver ها، مدیریت N+1 Query) خودش یک حوزه مجزا از یادگیری معماری میکروسرویس است و باعث فاصله گرفتن از هدف اصلی این پروژه خواهد شد.

**ترکیب REST برای لایه بیرونی و gRPC برای لایه داخلی** — انتخاب نهایی  
کلاینت با API Gateway از طریق REST صحبت می‌کند (سازگاری و سادگی برای مصرف‌کننده خارجی) و ارتباط بین Gateway و سرویس‌ها، و همچنین بین خود سرویس‌ها، از طریق gRPC انجام می‌شود (کارایی و قرارداد نوع‌دار برای ارتباط پرتکرار داخلی).

## تصمیم

- **Client ↔ API Gateway**: REST (JSON روی HTTP)
- **API Gateway ↔ سرویس‌ها**: gRPC
- **Order Service ↔ Product Service** (رزرو/آزادسازی موجودی): gRPC

قراردادهای gRPC (فایل‌های `.proto`) به‌صورت مشترک در `pkg/proto` نگهداری می‌شوند تا:

- هر سرویس به یک نسخه واحد و هماهنگ از قرارداد دسترسی داشته باشد
- کد Go تولیدشده از این فایل‌ها (توسط `scripts/generate-proto.sh`) در تمام سرویس‌های نیازمند، مشترک و یکسان باشد

## چرا این مرز دقیقاً اینجا کشیده شد؟

معیار انتخاب، «کیست که این ارتباط را برقرار می‌کند» است، نه صرفاً «کدام پروتکل بهتر است»:

- کلاینت‌های خارجی (مرورگر، اپلیکیشن موبایل) کنترلی روی زیرساخت سرور ندارند و REST بدون نیاز به کتابخانه یا ابزار خاص در تمام آن‌ها native پشتیبانی می‌شود
- سرویس‌های داخلی توسط خود ما نوشته و کامپایل می‌شوند، پس می‌توانیم از مزایای gRPC (قرارداد نوع‌دار، serialization سریع‌تر با Protocol Buffers، پشتیبانی native از streaming در صورت نیاز آینده) بدون هیچ محدودیتی در سمت مصرف‌کننده بهره ببریم

## پیامدها

### مزایا

- کلاینت‌های خارجی با ساده‌ترین و در دسترس‌ترین پروتکل (REST) کار می‌کنند؛ نیازی به کتابخانه گرفتن ویژه یا gRPC-Web نیست
- ارتباط داخلی از قرارداد نوع‌دار Protocol Buffers بهره می‌برد؛ تغییر ساختار پیام در زمان کامپایل مشخص می‌شود، نه در زمان اجرا
- کارایی بهتر ارتباط داخلی (که پرتکرارتر و حساس‌تر به تاخیر است) نسبت به JSON روی REST
- امکان استفاده از قابلیت‌های پیشرفته‌تر gRPC مثل Streaming در سناریوهای آینده (مثلاً ارسال به‌روزرسانی زنده وضعیت سفارش) بدون نیاز به معماری مجدد

### معایب

- سیستم اکنون دو پشته فناوری ارتباطی دارد (REST و gRPC) که هرکدام نیاز به ابزار و دانش جداگانه برای دیباگ دارند؛ برای مثال بررسی مستقیم ترافیک gRPC با ابزارهایی مثل `grpcurl` انجام می‌شود، نه curl معمولی
- نگهداری و هماهنگ‌سازی فایل‌های `.proto` در `pkg/proto` نیازمند یک فرآیند مشخص است (تولید مجدد کد پس از هر تغییر، از طریق `scripts/generate-proto.sh`)؛ فراموش کردن این مرحله می‌تواند باعث ناهماهنگی بین سرویس تولیدکننده و مصرف‌کننده پیام شود
- افزودن یک لایه ترجمه بین REST (در Gateway) و gRPC (به سمت سرویس‌ها) یعنی Gateway باید هم سرور REST باشد و هم کلاینت gRPC؛ این کمی پیچیدگی به کد Gateway نسبت به یک Reverse Proxy ساده اضافه می‌کند (که در ADR شماره ۰۰۰۲ نیز به آن اشاره شد)
